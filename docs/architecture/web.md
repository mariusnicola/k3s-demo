# Web


## Web
React 19, TypeScript, Vite, plain CSS with tokens, Radix primitives for dialog, tabs, tooltip. Routes: `/` goes to `/dashboard`, the landing page for every role; `/batches` list, `/batches/:farmId/:id` Batch, `/alerts`, `/design-system` catalog, not in the menu, `/signin`. Menu order: Dashboard, Batches, Alerts, Logs.
- Scripts in `app/web`: `npm run dev`, `build`, `test`, `lint`, `typecheck`. Dev server proxies `/api` and `/ws` to the ingress; `BT_INGRESS` overrides the target.
- Base URLs live in `src/config.ts` only. API `/api`, monitor socket `/ws` and line `/line` are all same-origin, derived from `location`, so no browser code holds an address or port. `VITE_MONITOR_WS` and `VITE_LINE_URL` override them for local work only.
- Layout: `src/ds` components and tokens, `src/pages` screens, `src/logic` pure rules, `src/live` sockets and data hooks, `src/api` client and types, `src/mocks` test fakes.
- Types in `src/api/types.ts` and `src/api/monitorTypes.ts` match the JSON of the API, Live, Line and monitor as built.
- The session is an HttpOnly cookie, so no script can read it. Load calls `/session`: `me` null means sign in, and it answers 200 either way, so a signed-out load logs no console error. Switch user posts `/api/auth/logout`. All tabs share one user, the last signed in.

## Browser reports
- `src/api/reports.ts` holds the contract in `docs/architecture/events.md` :: Browser reports. `main.tsx` starts it, so nothing posts in a test that did not ask.
- The browser makes the ID, so the page can show it whether or not the post lands. A repeat within 60 s shows the ID of the report that was sent and sends nothing, and only a report that went out, or is held to go out, is remembered. The key leaves out the correlation ID, because each try of a repeating failure has its own.
- Reported: a 5xx, no answer or the time limit, once and not per retry; a socket closing with any code but 4401, or failing to open; a render fault in `ErrorBoundary`; a value thrown in the page and shown as a page fault, under kind `render-fault`; `console.error`, an uncaught error and an unhandled rejection.
- Not reported, and no ID shown: an ordinary 4xx, which is the server answering; a cancelled read; a status a call lists in `answers`, as the ingress log's 503. A 4401 is the session ending. A call in `answers` is not retried either.
- One fault sends one report. A thrown value keeps its ID, by identity for an object and by value for a primitive. A primitive has no identity, so the same value counts as the same fault until 60 s pass with nothing drawing it. React's `console.error` for that fault is skipped, because `getDerivedStateFromError` runs before React logs. For a primitive that is the one call React makes, with the value alone, and any other line reports.
- A report during `beforeunload` is held, because Stop fires that event and the page lives on. `pagehide` discards what is held and sends nothing until `pageshow`. If the page is still alive after 2 s, held reports go out. The 2 s is a chosen number, not measured.
- The post goes past `send`, so a failed report is never reported. It writes nothing to the console. The browser's own "Failed to load resource" line on a refused post cannot be stopped from page code, so `tests/e2e/support/guard.ts` passes that route's 400, 403, 413 and 429 and nothing else.
- The "Your session ended" notice shows no report ID.
- `/logs?reportId=` reads the service log by report. The report's correlation ID then reads the Line and `/ingress/logs`. Until it is known, or if the report has none, the Line is not read and its frames are kept off.
- The Ingress panel on Logs shows for a report or a correlation ID. `src/logic/monitor/ingressReading.ts` turns the reads into one sentence, which claims only what they support. A request reads as stopped at the ingress only if `upstreamStatus` is `-` in every group of every row, compared as text. Ingress time is whole seconds, so rows sharing the newest second list their statuses and name no last one. Any other value reads as arrived with both statuses, never that a service answered, because nginx also records 502 and 504 for a failed connect. A null reads as arrived with the status alone. A service row outweighs all of these. A failed, filtered or short read, entries that left memory, a log not followed or a report near `since` never read as "never arrived". A report not found behind a filter, or after `browserEvicted` browser rows left memory, reads unknown, not lost. `evicted` counts service rows only, so it says nothing about a report.
- `browser-failure` is a service log reason, which the Line refuses, so a filter on it reads the service log alone. Picking it keeps Source and Level, so with `source=line` or `level=info` no log is read, and the page says so and names the control to change. That check uses the filters the Line was asked with, so a correlation ID beside a report still counts as a Line read.

## Live data
- Live data only by WebSocket. No polling, and no read on a hop, frame or reconnect: `checkNoReadInHandler` in `scripts/lint-rules.mjs` fails a read inside a handler.
- Frames: see `docs/architecture/events.md` :: Sockets. Each connect sends a snapshot, so a reopen needs no read.
- One `/ws/hops` socket while signed in, in `HopProvider` (`src/live/hopFeed.ts`), above the routes so a page change costs no reconnect. Signing out clears its rows.
- Summary, Alerts and the fail-next list come only from that socket. Batches and Batch read once on load, because a row older than the snapshot's 200 is in no frame, then merge pushed rows.
- Frames can arrive out of order, so the highest `version` wins, and the page keeps a pushed row after it leaves the 1,000 kept in memory.
- A write shows its own reply and ETag, with no read after it. A 412 reads the batch once. Fail next reads its batch first and refuses a final one, because a frame can still be on its way.
- A snapshot or summary with `reconciledAt` null means the store was not read yet: its zeros mean nothing, so tiles read Loading until one has it set. Hops flow meanwhile.
- A page that read a list or a batch offers one read at a press while its socket is lost and after it returns, because what the socket missed never arrives. Any read clears the offer.
- Line state comes only from `/line/ws`, opened only by the admin dashboard and Logs. A lost line socket reads Last known, or unknown if no frame ever came.
- Close 4401 ends the session and stops retrying, except on the monitor socket, which retries as a visitor. A refused upgrade looks like a network drop to the browser, so it stays lost and retrying until a call answers 401. Reconnect now makes that call.
- A burst of frames redraws at most four times a second.
- One monitor socket for the whole app, in `MonitorProvider` (`src/live/monitorFeed.ts`). It opens for every visitor, signed in or not, because the cluster work toast shows on every page. Only `ops.admin` gets the report and changes; everyone else gets `operations` frames only, and no field says which. Any change of session opens a new socket, since only a handshake carries the cookie, and clears operations, changes and the report; a first load is no change. A failed checklist the banner already holds stays until Seen, across sessions too, because `operations` frames are public. A sign-out closes the socket at once and opens the next only after logout answers, because the old cookie is good until then; a failed logout stays on no socket and reads Cluster work state unknown until a retry succeeds or someone signs in. After a 4401 the socket retries with backoff. Report freshness uses report frames only, so a socket with no report never reads as silent; a quiet non-admin socket shows only when it closes.
- Cluster work toast: `ClusterOperations`, fixed top right on all routes, sign-in included, 24rem wide at most. Past 70% of the screen height it scrolls inside, failure details stay folded, and the page under it never moves. Running shows spinner, name, step, elapsed; several at once join into one row. Done clears when the monitor drops it. Failed stays until Seen. A silent operation reads No signal, state unknown. A lost socket reads Cluster work state unknown, never no operation. It floats, so it never moves the page.
- Dashboard Changes panel: newest 50 of the feed, live, see `docs/architecture/monitoring.md` :: Change feed.
- Batches and Recent hops hold their rows while the pointer or focus is inside the table, and say so. Filter changes end the hold.
- A read waits out a `Retry-After` of 30 s or less, at most 9 waits. A longer one ends at once, and the page shows the wait and the words. `/me` never waits: a 429 there reads as not signed in, because a client over its limit can still sign in.
- Sockets retry after 200 ms, doubling up to 30 s, each wait cut by up to half at random. Reconnect now skips the wait.
- Every drop is reported at once. The page shows it only after `LOST_SHOWN_AFTER_MS`, 5 s, in `src/live/status/steadyStatus.ts`: a shorter drop heals itself. A warning clears on data, or after an open socket lasts that long. The status line counts resets, so a short drop is never silent.
- A connection state never moves the page: `ConnectionStatus` holds one box, its fault detail floats, panel notices float over their panel, and `LiveNote` holds a reserved line.
- When a socket drops, the panel says so and shows the time of the last data, never a stale green. Monitor data reads stale on an open socket when the last message or its `checkedAt` is older than 90 s. Stale values read as past: Was healthy, Was ready, Was over the cap.
- An event reads Delayed 120 s after its last step, not after `sentAt`, because every resend renews `sentAt`. A Worker outage holds delivery with no error to show.
- A batch list holds the newest 200, the API maximum. The Attention filter sees only those rows, so Blocked and Flagged totals link to Alerts.
- A matching chain link compares stored strings only, so it reads neutral, never verified.
- Closed or Rejected with a pending event says its record is not written yet.
- Replay clears fail-next, so a Blocked batch neither shows it nor accepts it.
- A render fault or failed page chunk shows Reload page, reset when the address changes.

## Dashboard
- Every part of the map explains itself: hover, keyboard focus or a tap opens a tip with its name, what it is, what it does, and one live line where the report holds one. Missing live data is left out; a stale report's pod reads Last known. The words live in `logic/terrain/partInfo.ts`, one entry per part, and a test against `deploy/caps.json` and every drawn part fails until a new part has an entry. A machine with no entry says so under its own name. The tip stands on the page body and is kept on screen by `logic/terrain/tipPlace.ts`, so the map's edge cannot cut it. Each part is a focusable button in a named group, named by the words it shows, with its explanation as its description, so every part is one Tab stop. Escape or a press outside closes it. A scroll or a resize moves it with its part, because focus scrolls a part into view. Links and dots have no tip.
- Line rate is a lever, a native range from 0 to 35 batches per second in steps of 0.2, with a printed scale and the value in words. 0 runs the line idle. With the line running, the rate goes once when a drag or key ends, and a release during a call waits, so only the latest goes next. With the line stopped nothing goes: `POST /line` also starts it, so Start line sends the lever's value. A failed call puts the lever back at the rate the line reports and says so. A frame does not move the lever during a drag. A rate above 35 rests the handle at 35 and keeps its true figure in the words. Rights stay on the server: `ops.admin`.
- Workers card, admin only, above the map: reads the monitor report. One element per Worker pod in `batch-tracker`, with node and state. Running counts Workers serving, as the map does. Dispatcher leader is `dispatcherLeader`; standbys are the other Dispatchers serving, Unknown with no leader. Busy means a Worker passed an event in the last minute or has work in flight now, not that it works this instant. Busy and Idle count the Workers running by `busy`, and each block says its own in words and icon. A running Worker with `busy` null or missing is no guess: it counts under Busy not known, and Busy and Idle read At least N, or Unknown when none is known. Most possible is `workers.max`, Unknown when null or missing, never 0. Before the first report it waits, or reads Unknown with the monitor lost. A report with no pods reads as missing, not as zero. A report with pods and no Worker reads 0. A stale report keeps the Workers as last known, reads Stale on its figures, and calls nothing ready.
- `/dashboard` picks by permission, see `docs/architecture/design-system.md` :: Dashboards by role. Operator, inspector and read only views read `/ws/hops` and `GET /batches`, never `/line/ws`, `/line/logs` or `/metrics/series`.
- The sections below describe the admin view.
- One dot per trace, one batch step, placed by the hop's `to`, in `seq` order within the trace. A hop from an older pod has no `to` or `seq`: `OLD_LEG` in `logic/flow/dots.ts` gives its leg, and time then hop order give its place. Dispatcher to Worker and back run through the real ingress pod. A failed hop draws a diamond. At most 80 dots; the rest are counted as not drawn. Reduced motion: no pulse, no tween, dots step between stations.
- `[x] RealTime Monitor` on: dots at live speed. Off: buffered playback with speed 0.25x, 0.5x, 1x, 2x.
- Playback buffer keeps the last 5,000 hops, starts at the oldest, skips idle gaps over 2 s and says how many hops it skipped, which are this page's own and never a system loss. Playback hides station counts and says how old its dots are.
- Each snapshot repeats the last 500 hops. Web drops repeats, and hops over 2 s behind the newest in their frame go to the list without a dot.
- Station words: API, Dispatcher and Worker show pods ready from the report; the store the check of the store in use; Service Bus "Emulator answers", because that check reads the `monitor` queue; every station reads Stale when the report is not fresh, and Failing when its check fails.
- Numbers name what they count: accepted, saved, records written, marked sent, sent to queue, delivered, read. They cover this view, since the time printed under the map. A number on a plate covers that plate's pods.
- Service Bus shows what waits: sends this page saw with no delivery yet, dropped after 5 min as a delivery it missed.
- The map draws each real connection as a still line; only a dot, from a real hop, moves. The `api` hop walks from the load balancer through the ingress and the pod that took it to the store, and the store's saved count is that hop's. Record is a write into the store, not a block. The report names the store in use (`store`): that one is the station, named from the report. The store not in use stands as a plain container with no link and no count, and with no store reported the station reads Store and claims no health. Plates: each node with app pods, ingress, MetalLB, Prometheus and KEDA, with drawn and total pods; Docker with both stores, Service Bus, its SQL, Line, Monitor; Load balancer with the address MetalLB holds; Browser.
- Outside clients, Line and monitor included, reach the ingress through the load balancer, so a client hop starts there. The Dispatcher reaches a Worker through the ingress by its in-cluster name, so that leg never touches the load balancer. Only the speaker on the ingress pod's node links to the address, because the Service has `externalTrafficPolicy: Local`. ClusterIP Services are not drawn: the ingress goes to pod endpoints, not through them.
- Blocked and a Worker pause hold a reserved line above the map, so they outlast a dot.
- Pods table: Failed first, then Unknown, then not ready. Failed is danger and named in a notice above the table, Unknown is a warning. Phase is never green; only the Ready column is. A report with no `ready` reads Not reported. Lost data reads Was, with no notice.
- Performance panel: one `GET /metrics/series` per bucket chosen, then `metricPoint` and `stagePoint` frames on `/ws`, see `docs/architecture/monitoring.md` :: Performance series. A 503 is the Monitor's answer: shown at once, not retried, and Try again reads once more. Bucket remembered in this browser, default 10s. A `metricPoint` is a whole minute, so 10s and 30s views ignore it, and the 30s view says all of it is as read. A `stagePoint` is one 10 s bucket with its stages, pending and counts: at 10s it appends a bucket to every chart, buckets missed between frames stay as gaps, and a wider view stays as read because percentiles are never summed.
- Where the time goes: three charts on one time axis (batches started and closed per second, stage p95, pending peak), the slowest stage now and the worst bucket on screen named in words, and the latest figure of each. Stages: API call, Database write, Waiting in the queue, Worker handling. p50 is not drawn. A p95 of exactly 60 reads `>= 60 s`. A stage with no samples says No data, never zero. A Monitor that sends no `stages` reads Stage timing is not reported.
- Performance shows events created and passed, batches created, shipped, closed, rejected, Dose 1, Dose 2, inspections passed and failed. Dead lettered and replayed counters are not shown.
- A measure with no series, or with every bucket null, reads Unknown. A null bucket is a gap in the line and Unknown in the values table. Buckets missed while the socket is lost stay null: no read on reopen.

## Logs
- `/logs` reads `GET /line/logs` and `GET /live/logs`, admin only. The Logs link shows only with `ops.admin`; a direct visit without it goes to `/dashboard`. Dashboard Errors links to `/logs?level=error&source=line`. Filters live in the address. `source=line` shows Line entries only, so the Dashboard link lands on what its counter counted; it is never sent to a service.
- One read per filter, then `/line/ws` frames merge in, through the same filter test as the line. Frames that land during the read wait for it.
- Service entries merge into the list by time, are never pushed, and read again at a press. Information and any Line reason skip that read: the service log holds neither and answers 400. A failed service read leaves the Line's entries, counts and feed alone and says what is shown. A failed Line read leaves service rows on screen, with the problem and its ID above them. Counts and the Dashboard comparison stay Line only, and the page says so. A farm or batch filter with no service rows says many service entries name neither.
- `entriesDropped` on a line frame, or a reopened snapshot that starts after the list, offers one read to fill the gap, never automatically. It reads the newest entries, so it names no count of what it cannot bring back.
- Errors counter is the line's count since it started. Memory keeps the newest 5,000 entries of every level, so errors can leave it. Logs compares the counter with matched entries and says why they differ, and uses `errorsByReason` for reason counts unless a farm, batch or time filter narrows them.
- The line sends no sentence per reason, so `src/logic/monitor/logs.ts` holds them. Reason codes outside that list and backwards ranges never reach the service, because it answers 400.

## Refusals
- Every request has one time limit, `REQUEST_LIMIT_MS`, set past the ingress so its answer arrives first. A request past it fails with the ID sent and is never retried; a write says its result is unknown.
`src/api/problem.ts` maps each status to title, message and way out. 403 and 404: Back to batches. 409, 412, 428: Reload batch. 401: sign in, then back to the same address. Failed reads: Try again. Failed writes: Dismiss, then repeat with the same control.
A pressed control that vanishes hands focus to the main region. Buttons a user cannot use stay visible and focusable, with the reason beside them.
